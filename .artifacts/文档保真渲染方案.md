# 文档保真渲染（Excel/Word 原样绘制）— 可行性评估与方向方案

> 2026-10-20 | 面向：徐工 | 涉及模块：现场无纸化 · 模板管理 / 填写提交 / 电子档
> 本文只做方向评估，不含代码改动。

## 一、结论先行

**思路可行，推荐走 HTML 渲染路线。但"原样"不是开关而是连续变量，建议先花 1 天做只读保真预览，用真实文件看清保真度上限，再决定填写页要不要迁移。**

三条不建议的路线先说清楚：GDI+ 自绘（保真上限低、工作量大）、直接嵌 Office/OLE（100% 保真但取不到数据、依赖 Office 安装）、文档栅格化成图片盖输入层（对不准、不可选不可搜、打印糊）。

另外必须先点明一个架构事实：**当前项目零 NuGet 依赖**（csproj 里没有任何 `PackageReference`），WebView2 现在是靠反射加载的"可选增强"，缺失就自动降级。填写页若改成 HTML，等于把 WebView2 从"可选"变成"核心依赖"——这是本次方案里最需要你拍板的一件事。

## 二、判断依据（基于当前代码现状，不是泛泛而谈）

| # | 事实 | 对方案的含义 |
|---|---|---|
| 1 | 现在丢格式是**设计使然**：`ChecklistTemplate` 是语义模型（列/行/抬头/表尾），填写页用 DataGridView 渲染 | DataGridView 只能表达"等宽矩形网格"，天然画不出合并单元格、列宽比例、字体差异。不是 bug，是选错了模型 |
| 2 | **渲染所需的最小几何数据已经有了**：`RawSheet` 已含 0 基完整网格 + 合并区域 + 表名 | 只需再加一层"样式索引"即可出图，**不必推翻数据层** |
| 3 | xlsx 样式**读侧完全空白**：`xl/styles.xml`（cellXfs → font/fill/border/alignment/numFmt）从未被读取，只有 `XlsxWriter` 在"写"的时候生成过 | 样式解析要从零写，这是整个活儿最大的工作量块（约 60%） |
| 4 | docx 解析**只拼了文本**：现在只取 `w:t`，`w:tblGrid`（列宽）、`w:tcPr`（gridSpan/vMerge/shd/tcBorders）、`w:pPr`、`w:rPr` 一个都没读 | Word 表格的保真渲染约等于重写表格解析；且 docx 比 xlsx 更"活"（无固定列宽、可嵌套） |
| 5 | 电子档已有**自包含 HTML 导出**能力（`EArchiveForm.ExportHtml`，零外链、内联样式） | 渲染路线可跨代复用：填写页与归档共用一套 HTML 模板，视觉天然一致 |
| 6 | 打印现在是 `PrintDocument` + 列宽等分逐格画（`PrintArchive`） | 本质同样是丢格式。改 HTML 后走 `window.print()` + CSS 分页，反而更接近原件、代码更少 |
| 7 | 导入解析零依赖（ZIP+XML 手写），AI 复核、批量填充、快照隔离都挂在语义模型上 | **渲染层不许污染数据层**：`ChecklistTemplate` / `Values` / 快照格式一行都不要动，否则 AI 复核、批量填充、历史还原全部要跟着改 |

## 三、保真度分四级（把"原样"量化，避免各说各话）

| 级别 | 内容 | 能否做到 | 增量成本 |
|---|---|---|---|
| **L0 结构保真** | 合并单元格、列宽比例、行高、网格线 | ✅ 能做 | ~1 天 |
| **L1 视觉保真** | 字体/字号/粗斜体/字色/填充色/对齐/自动换行 | ✅ 能做（需写样式映射） | +2~3 天 |
| **L2 打印保真** | 分页、表头重复、页边距、横向/纵向 | ✅ 能做（CSS 分页） | +1~2 天 |
| **L3 极端元素** | 图表、图片、条件格式、数据验证下拉、旋转文字、页眉页脚/域、嵌套表 | ⚠ 建议放弃或占位降级 | 不建议投入 |

**我的判断：L0+L1+L2 覆盖点检表 95% 的视觉诉求，L3 基本用不到（点检表字多图少）。**

## 四、四条候选路线对比

| 路线 | 保真上限 | 工作量 | 与现有架构契合 | 能填+能结构化存数 | 结论 |
|---|---|---|---|---|---|
| **A. HTML 渲染 + 单元格内嵌输入** | 高（L2） | 中 | **高**（复用 HTML 导出能力、复用现有 Values 键） | ✅ 是 | **推荐** |
| B. GDI+ 自绘 + 覆盖 WinForms 控件 | 中（L1，字体渲染与文本换行要自己写） | 高 | 中 | ✅ 但坐标对齐麻烦 | 不推荐 |
| C. 嵌 Office / OLE 原件 | 最高（100% 原件） | 低 | 极低（脱离系统、取不到数） | ❌ 否 | 不推荐 |
| D. 转图片当背景 + 透明输入层 | 最高（像素级） | 中（需 LibreOffice/Office 转换） | 低 | ⚠ 勉强（对不准、不可选不可搜、导出糊） | 仅作兜底展示 |

## 五、路线 A 的关键实现方向

### 1. 数据层：`RawSheet` → `StyledSheet`（只加不改）
```
CellStyle { FontFamily, FontSize, Bold, Italic, Underline, Color, FillColor,
            HAlign, VAlign, WrapText, Borders(上下左右 + 线型), NumFmtId }
StyledSheet { 网格 + 合并 + 每格 StyleIndex + 列宽[] + 行高[] + 样式表(去重) }
```
- 样式表**去重**：一份 Excel 通常只有 10~30 种 `xf`，去重后体积极小
- `ChecklistTemplate` 完全不动，继续管"哪列要填、什么类型、必填、候选项"

### 2. 渲染层：`SheetHtmlRenderer`
- `<table>` + `<colgroup>`（列宽）+ 单元格 `rowspan/colspan` + 内联 `style`
- 合并单元格：值写左上角格，其余格留空但保留边框（否则线会断）
- 文本换行：`white-space: pre-wrap`；行高优先用文件里存的 `row@ht`，没存就交给浏览器自适应
- **纪律**：不引任何外链 CSS/JS（与数字孪生页同一条），全部内联；单元格文本必须 HTML 转义（导入的是任意文件，否则能注入 `<script>`）

### 3. 填写层：`<td>` 内嵌控件（不要用绝对定位覆盖层）
- 按列的 `FieldKind` 决定控件：`<select>` / `<input type=number|date|text>` / `<textarea>`
- 每格带 `data-key="r{row}c{col}"`，**沿用现有 `Values` 键格式**，JS 收集成 JSON 回传（`WebMessageReceived`）
- 校验双侧：JS 即时红框 + C# 提交时权威校验（前端校验只做体验，不能当准）

### 4. 归档层：同一套 HTML
- 电子档用同一渲染器（快照里的 `StyledSheet` + 提交值），视觉与填写页一致
- 打印走 `window.print()`，代码反而比现在的 `PrintDocument` 简单
- **历史提交不重渲染**：保持"提交那一刻的样子"，一致性优先（快照里没存样式，重渲染反而会变样）

### 5. 降级：保留现有 DataGridView 填写页
WebView2 不可用时自动回落到现在的填写页，能力不丢——这条必须保留，否则现场机器缺运行时就是死路。

## 六、技术难点（按风险排序 + 对策）

| # | 难点 | 风险 | 对策 |
|---|---|---|---|
| 1 | **样式解析与映射**（占 60% 工作量）：xlsx 五组索引交叉引用；docx 三级属性继承（docDefaults → style → 直接格式） | 高 | 只覆盖点检表实际用到的子集（字体/字号/粗体/边框/填充/对齐/换行），其余给默认值兜底；再加一个"样式覆盖率自检" |
| 2 | **合并单元格错位**：rowspan/colspan 少写一格，整张表就歪 | 高 | 渲染后自检"每行列数之和 == 网格列数"，不通过就报警并降级为无合并普通表格 |
| 3 | **列宽/行高换算**：Excel 列宽是"字符数×256"、行高是 pt；docx 是 twips | 中 | 统一换算成 pt 交给浏览器，**不要自己乘 DPI**（会双重缩放） |
| 4 | **docx 表格比 xlsx 更"活"**：`tblGrid` 可能缺失、单元格内可多段落/嵌嵌套表 | 中 | 只支持单层表 + 段落文本，嵌套表降级纯文本 |
| 5 | **数字格式还原**：只取缓存值，`numFmt` 不映射的话日期变「46345」、百分比变「0.55」 | 中 | 映射常用 numFmt（日期/千分位/百分比/小数位），其余原样输出 |
| 6 | **输入控件与单元格内边距冲突**：`td` 有 padding、`input` 有 border，可填格会"胖一圈" | 中 | 可填格 `padding:0`，input `border:none; background:transparent`，用 td 边框充当输入框边框 |
| 7 | **WebView2 成为核心依赖**：现在项目零 NuGet，填写页却要靠它 | 高（架构） | 见第七节待拍板；必须保留 DataGridView 降级路径 |
| 8 | **性能**：几百份提交的列表预览不要用 WebView2 | 低 | 列表仍用 DataGridView，只有"单份填写/单份归档"用 HTML |
| 9 | **打印分页切在行中间** | 低 | `thead{display:table-header-group}` + `tr{page-break-inside:avoid}` |
| 10 | **安全**：单元格文本注入 | 中 | 全量 HTML 转义 + 禁止外部资源 |

## 七、需要你拍板的四件事

1. **"像"要到什么程度？**
   - 70 分：现有 DataGridView 加列宽/换行/边框，成本极低（半天）
   - 95 分：HTML 保真（L0+L1+L2），多 3~5 天
   如果只是为了"看着像表"，70 分可能就够了。
2. **是否接受 WebView2 成为填写页的核心依赖？**（现在是可选）现场产线机器有没有 WebView2 运行时？如果没有，就要么预装、要么走 70 分路线。
3. **归档电子档是否必须与原件像素级一致？**（审厂/政府场合可能会拿原件比对）
4. **历史电子档要不要按新样式重渲染？** 我建议**不重渲染**，保持提交时的样子。

## 九、我的建议

**先做 P0（1 天）**。理由很直接：保真度这件事，看一天就能判断，猜一周也不准。拿 `车间设备与环境班前点检表2.xlsx` 和你后续给的真实文件试，如果 L1 只到"七八分像"，那就说明这条路对你这个场景性价比不高，及时收手只花 1 天。

**两条纪律**（无论选哪条路线）：
1. **渲染层不动数据层**：`ChecklistTemplate` / `Values` / 快照格式一行不改，否则 AI 复核、批量填充、快照隔离全要连带重做。
2. **保留降级路径**：HTML 拿不到就回落 DataGridView，绝不出现"环境不对就完全不能用"。
