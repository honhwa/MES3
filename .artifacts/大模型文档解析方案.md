# 大模型驱动的点检表结构解析 — 可行性、实现思路与关键注意事项

> 2026-10-20 | 面向：徐工 | 涉及模块：现场无纸化 · 模板管理

## 一、结论先行

**可行，而且这个场景特别适合大模型——但必须守住一条铁律：模型只做"理解与标注"，规则做"校验与落库"，人做"确认"。**

原因很直接：点检表是**版式千变万化、语义高度业务化**的文档。今天的规则解析器已经能覆盖"标题 / 抬头 / 表头 / 表体 / 表尾"四段结构（你那份 23 行的表已 100% 正确），但它靠的是"非空单元格数 ≥ max(3, 列数×60%)"这类几何启发式——遇到下面四种版式就会退化：

| 版式                        | 规则解析器的表现          | 大模型的表现      |
| ------------------------- | ----------------- | ----------- |
| 表头 2 行合并（父列"检查"下挂"外观/尺寸"） | 会把父列当独立列，或把子列行当数据 | 能识别父子层级     |
| 横向表（项目在行、设备在列）            | 会当成 2 列           | 能识别方向并转置建议  |
| 一表多段（表中间夹一段说明再续表）         | 表体在第一个空行处截断       | 能识别"续表"     |
| 列名语义模糊（"判定基准" vs "点检结果"）  | 关键词猜，易错           | 读语义判断"哪列要填" |

**并且——基础设施已经就绪。** 系统里已有共用的大模型通道，不是从零搭：

- `Models/LlmHttp.cs` — 共用 HTTP 通道（超时/错误分类统一）
- `Models/LlmService.cs` — `CallJson<T>()` 已内置四道护栏：  
  ① 容错提取 JSON（兼容 \`\`\`json 包裹、前后废话、尾逗号）  
  ② 业务校验钩子（返回 `(值, 置信度, 原因)`）  
  ③ **置信度门槛**（默认 0.60，模型自己不确定就不采纳）  
  ④ **未授权数字拦截**（模型编数字 → 整段丢弃）  
  ⑤ **任何异常都返回 `Ok=false`，绝不抛到业务层**

也就是说"模型不可用就降级到规则解析"这件事，架构上已经成立，不需要新造。

## 二、整体实现思路（四层 + 人在环）

### 层 1｜输入侧：把表格压成"带坐标的紧凑文本"

**不给模型看原始 XML，也不给二进制。** 统一序列化成下面这种形态（一份 23×10 的表约 2~4k token）：

```
SHEET=班前点检表  DIM=A1:J29
MERGED=A1:J1, A2:C2, D2:F2, G2:H2, I2:J2, B4:B7, B8:B11, ...
R1  | A1=车间设备与环境班前点检表
R2  | A2=车间/线别：____ | D2=点检日期：__年_月_日 | G2=班次：□早班 □中班 □晚班
R3  | A3=序号 | B3=点检项目 | C3=点检内容及标准 | ... | J3=确认人
R4  | A4=1 | B4=静电防护 (ESD) | C4=作业人员防静电服、帽、鞋穿戴规范、无破损 | ...
```

要点：

- 空单元格不输出（省 token）
- **每个值都带 `R/C` 坐标**——这是后面"原文定位"和"防幻觉核对"的唯一依据
- 合并区域单独一行给出（模型判断"这是抬头还是表头"的关键线索）
- 大表分块：按连续行块切分，每块重复表头，单块 ≤ 200 行

### 层 2｜模型侧：只输出"强约束结构化标注"

System prompt 的核心不是"你帮我解析"，而是三条硬约束：

1. **只允许使用输入中出现的原文**——不得改写、不得翻译、不得补全、不得新增
2. **每一条判断都必须给 `sourceRef`（如 `R4C2`）**，指向它下判断所依据的单元格
3. **不确定就标低置信度，不要猜**

输出 schema（示意）：

```json
{
  "title":      { "text": "…", "sourceRef": "R1C1" },
  "headerFields": [ { "label": "车间/线别", "hint": "____", "sourceRef": "R2C1" } ],
  "headerRow":  { "row": 3, "sourceRef": "R3" },
  "columns": [
    { "col": 1, "header": "序号",        "kind": "Context",  "fillable": false, "confidence": 0.98 },
    { "col": 7, "header": "点检结果 (OK/NG)", "kind": "Select", "fillable": true,
      "options": ["OK","NG"], "required": true, "sourceRef": "R3C7", "confidence": 0.95 }
  ],
  "bodyRange": { "fromRow": 4, "toRow": 26 },
  "footerNotes": [ { "text": "点检说明：…", "sourceRef": "R28C1" } ]
}
```

温度 0~~0.2、`max_tokens` 按表格规模动态给、超时 20~~30s。

### 层 3｜校验侧：四道核对（能不能用的分水岭）

模型输出**一律先过校验，不通过的一律不采纳**：

| 核对            | 做法                                         | 不通过的处置           |
| ------------- | ------------------------------------------ | ---------------- |
| ① 原文可溯        | 每条 `header/hint/text` 规范化后必须能在输入坐标集合里找到    | 标红"模型编造"，不采纳     |
| ② **完整性双向核对** | 模型给出的可填项数 vs 规则扫描出的候选（可填列 × 数据行）**差集全列出来** | 差集进"待确认"区，绝不静默丢弃 |
| ③ 类型双口径       | 模型的 `kind` vs 关键词规则的 `kind` 不一致 → 标黄       | 默认取规则值，用户一键切换    |
| ④ 位置合法性       | `col` 在 `[0,列数)`；`row` 落在表体内；不得指向表头/表尾行    | 越界项丢弃并计数提示       |

> ②是**最要紧的一条**。模型出问题最危险的不是"编一个不存在的项"，而是"**悄悄漏掉一个必填项**"——现场少填一项，事后根本追不出来。所以完整性不能靠模型自证，必须用规则扫描做独立第二意见。

### 层 4｜落库侧：人在环，模型绝不直接入库

- 模型结果**只进"预览确认页"，绝不直接 `SaveTemplate`**
- 预览页三色标注：**绿**=模型与规则一致可直接采纳｜**黄**=两者不一致或低置信｜**红**=原文找不到（幻觉嫌疑）
- 操作：逐个确认，或"全部采纳绿项"，黄/红必须人工过一眼
- **点任意一项 → 右侧高亮原表对应单元格**（sourceRef 反查），这是审厂/政府场合被追问时的答案
- 保存时写审计：文件 SHA256、模型名与版本、提示词版本、耗时、采纳/否决清单

### 交互流（一句话）

```
导入文件 → 规则解析（秒出，先给一版可用结果）
        → 后台异步问模型（2~6s，可取消）
        → 两版结果做差集 → 三色确认页 → 人工确认 → 保存模板
```

**规则解析永远是"第一个到达的结果"，模型是增强不是前置依赖。** 这样断网、Key 过期、模型超时，页面都照常能用。

## 三、关键注意事项（按风险排序）

| #  | 风险                 | 说明与对策                                                                               |
| -- | ------------------ | ----------------------------------------------------------------------------------- |
| 1  | **漏项 > 编项**        | 漏一个必填项现场就少填一项且无法追溯。对策：规则扫描做独立完整的第二意见，差集必须显式呈现，禁止静默合并                                |
| 2  | **不要让模型产出"显示文本"**  | 列名/项名一律取**原文单元格值**，模型只判断"这列是什么用途"。否则模型改一个字，历史模板与快照就对不上，可追溯性直接崩                      |
| 3  | **定位必须字符级可回溯**     | 没有 `sourceRef` 的模型结论不可信。要能"点一项→高亮原文格"，这是可审计性的地基                                     |
| 4  | **离线和降级是硬要求**      | 演示现场常无外网。必须先跑通纯规则解析，模型仅增强（现有 `LlmService` 已经做到"未配置即降级"）                             |
| 5  | **成本与延迟**          | 一份 23×10 表约 2~~4k 输入 token、2~~6 秒。必须做**文件 SHA256 → 解析结果缓存**，同版式直接复用；同版式再次导入应命中缓存零调用 |
| 6  | **隐私与脱敏**          | 点检表含产线名、设备号、人员姓名。送模型前走脱敏开关（客户/政府场合默认开"仅本地规则解析"），并留"本次解析是否出网"的记录                     |
| 7  | **模型/提示词版本要留痕**    | 同一文件不同版本可能给不同结构，出问题必须能复现。审计里记 model + promptVersion                                 |
| 8  | **多级表头是最大工作量**     | 模型能给父子层级，但**渲染侧要做两级表头**（DataGridView 需要列组合并或自绘）。建议单级先上，多级单独一期                       |
| 9  | **不能在 UI 线程同步调模型** | 2~6 秒会让界面假死。必须异步 + 进度 + 可取消，且失败不能弹错误框（降级为规则结果 + 状态栏提示即可）                            |
| 10 | **失败零副作用**         | 解析失败保持原模板不动，绝不允许"半张表"入库。与既有"过账先整体校验再统一扣减"同一原则                                       |
